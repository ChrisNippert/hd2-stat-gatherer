# Stat Gatherer — project context

## Original brief

Track Helldivers 2 drop-rate stats while playing (super credits vs. requisition vs. medals vs. weapons), per mission, across Points of Interest (2-man bunkers = 3 slots, explodable bunkers = 2 slots, loot pods = 1 slot). Fast tally UI (+1 buttons) usable live during gameplay, "New Mission" saves and resets, per-hour/min/sec accumulation rates, Helldivers-2-styled UI. See README.md for the full current feature set — this file is oriented toward a future Claude session picking the project back up, not toward end users.

## Stack decisions and why

- **Vanilla HTML/CSS/JS, ES modules, no build step, no framework.** User wanted something GitHub-Pages-hostable and simple. Deliberately kept this way even as features grew — resist the urge to introduce a bundler/framework unless the user asks.
- **`node:sqlite` (Node's built-in module) instead of `better-sqlite3`.** `better-sqlite3` failed to install in this dev environment (no prebuilt binary for the Node version in use, and native compilation wasn't available). `node:sqlite` needs Node ≥ 22.5 but avoids native deps entirely — a better fit for "my own server" self-hosting anyway. If reintroducing a native dependency ever comes up, remember this failure mode.
- **No server-side canonical config.** The server (`server/server.js`) is a dumb mission store — it just persists whatever `poiCounts`/`itemDrops`/`squadMode` a client sends, keyed by mission ID (upsert). Aggregation across divers for Global Stats works because POI/item *IDs* (e.g. `loot_pod`, `medals`) are assumed consistent across clients, not because the server enforces a shared taxonomy. Custom item/POI types a user adds locally are effectively private to their own stats unless another diver happens to add the identical ID.
- **No authentication.** Diver ID is a random client-generated UUID, no password. This was an explicit user choice ("no private data, security isn't super important"). Don't add auth/accounts unprompted — if asked to hardn the server, the agreed-upon cheap mitigation (not yet implemented) was a shared-secret header check on the POST endpoint, plus recommending Cloudflare Tunnel over direct port-forwarding for exposure safety.
- **The app ships pointed at a real public server by default**: `state.DEFAULT_SERVER_URL = 'https://hd2stats.chrisnippert.com'` (the user's own domain, fronting their self-hosted instance). `getServerUrl()` only falls back to it when `localStorage` has never had the key set at all — an explicitly-saved empty string (user cleared the field and hit Save to go offline) or a custom URL both still win. This means a fresh install syncs to the real production server immediately with zero setup; **be careful with any local testing that doesn't explicitly override Settings → Server to a local/test URL first**, since `init()` fires a background sync on load using whatever `getServerUrl()` returns at that moment — harmless (just a health-check GET) if there's no pending local mission data yet, but don't let test data get POSTed there.

## Things that look like bugs but aren't

- `assets/icons/*.webp` files have a `.webp` extension and *are* WebP despite originally being fetched from URLs ending in `.png` — Fandom's CDN serves WebP regardless of the URL's apparent extension. Already renamed correctly; don't re-fetch and re-save as literal PNG.
- **Fandom's "Icon" files for Rare/Super Samples are corrupted at the source** (`Rare Sample Icon.png` / `Super Sample Icon.png` on `helldivers.fandom.com` — genuinely broken uploads, not a fetch/decode issue on this end: they render as flat color quadrants divided by a white cross, the classic WebP block-corruption pattern, confirmed by re-downloading and by checking file size ~100-180 bytes vs ~2-4KB for working icons). `Common Sample Icon.png` on the same wiki is fine. For Rare/Common Samples, the working source ended up being **`helldivers.wiki.gg`'s `Common_Sample_Icon.svg` / `Rare_Sample_Icon.svg`** (found via that wiki's `Sample` page infobox → `{{Currency|...}}` template rendering, not the `allimages` API search) — note wiki.gg also hosts `Common Samples.png`/`Rare Samples.png` under similar names, but those are photorealistic world-object renders, not flat icons; don't confuse the two. If adding Super Samples later, its Fandom icon is broken the same way — check wiki.gg's SVG first.
- Icon images are cropped tight to their non-transparent content (see git history around the "requisition icon looks weirdly offset" fix) — the source wiki images had huge transparent padding that broke consistent sizing. If replacing an icon asset, crop it the same way (Pillow `.getbbox()` + crop) or sizing will look inconsistent again.
- `js/main.js` wires nearly all DOM event listeners through an `on(id, event, handler)` helper (and init steps through `safe(fn, label)`) instead of raw `el(id).addEventListener(...)`. This is deliberate, not incidental — a stale cached `index.html` paired with a freshly-fetched `main.js` (normal during a rollout) previously caused a single missing element to throw and silently abort the entire script before `init()` ran, blanking the whole page. Keep new top-level listener wiring going through `on()`/`safe()`. **This does not protect against a stale cache at the ES-module level** (browser has an old cached `config.js`/`state.js`/`stats.js`/`api.js` while `main.js` is fresh, or vice versa) — a named-import mismatch there aborts the whole module graph before any of `on()`/`safe()` even runs, and looks identical to the DOM case from the outside (blank UI, nothing rendered). See the cache-busting entry below, which is what actually covers this case.
- **Cache-busting**: `index.html`'s `<link>`/`<script>` tags and every internal `import ... from './x.js'` in `main.js` carry a shared `?v=YYYYMMDD`-style query string (see `index.html` and the top of `main.js`). **Bump this string on every change to any file in `js/` or `css/style.css`** — the version is what forces browsers to fetch fresh copies instead of serving a mismatched mix of cached and fresh files, which otherwise manifests as "the UI doesn't work at all" with no console error a user would think to report. This was added after that exact symptom occurred twice.
- There is no mission timer or pause/resume feature — removed entirely per user request (it was in the app for a while; stats' per-hour/min/sec rates were stripped even earlier at the data layer). Don't reintroduce `durationMs`-based UI or pause-adjusted timing without being asked; missions still get a plain `startedAt`/`endedAt` from their lifecycle but nothing surfaces it.
- `squadMode` on a mission can be `'solo' | 'solo_warp' | 'multiplayer' | 'unknown'` — `'unknown'` specifically means "recorded before squad-mode tracking existed," not "guessed solo." Don't default missing squadMode to `'solo'`; that was a deliberate choice so old data doesn't get silently mislabeled. The user later used the Settings → Re-tag Missions tool to manually bulk-relabel their own unlabeled history once they confirmed it was actually all solo. `difficulty`/`faction`/`planet` follow the same "blank/missing means genuinely unlabeled" pattern, backfillable via Settings → Backfill Existing Missions (fills only currently-blank fields, never overwrites).
- Item `value` (used for Resource Value stats) is **not stored or user-editable at all** — `stats.resolveItemValues()` computes it fresh on every render: prefer the global (crowd-pooled, all divers) Drop Size Tracker average, fall back to the local-only average, fall back to the item's seeded default in `DEFAULT_ITEM_VALUES` if nobody has any observations yet. There used to be a manual "Value" field and an "Apply as Value" button; both were removed in favor of this automatic calibration. Don't reintroduce manual value editing without being asked.
- Charts (`js/main.js`: `barChartHtml`, `dropProbabilityHeatmapHtml`) are hand-rolled HTML/CSS, not a library or SVG — bars are `<div>` width percentages, the heatmap uses CSS `color-mix()`. Colors come from the dataviz skill's validated dark-mode categorical palette, re-validated against this app's actual panel surface `#12140e` (see `--chart-seq`/`--chart-cat-*` in `css/style.css`) rather than the skill's generic default surface. If adding more chart types, follow the same skill before picking colors.
- Mission editing/deleting lives on the MISSIONS page (`renderLogPage`, `missionEditFormHtml` in `main.js`). Deleting calls `DELETE /api/missions/:id?clientId=...` on the server (best-effort — no retry queue if it fails offline, consistent with the app's low-stakes tolerance for sync gaps elsewhere). Server checks the mission's stored `client_id` matches the requesting `clientId` before allowing update (POST, when the id already exists) or delete — 403 otherwise. This is ownership-by-knowing-the-UUID, same trust model as the rest of the app (no passwords), just scoped so one diver can't edit/delete another's data by guessing or colliding on a mission id.
- `DEFAULT_PLANETS` in `js/config.js` is the full 266-planet list scraped from `helldivers.fandom.com/wiki/Planets_and_Sectors` via its MediaWiki API (`/api.php?action=parse...&prop=wikitext`) — direct `curl`/WebFetch on wiki pages hits a Cloudflare bot challenge, the API endpoint doesn't. IDs are generated with the app's own `slugify()` so they match IDs a user may have already created by hand (e.g. `phact_bay`). The Planet field is a searchable `<input list="planet-datalist">` (not a `<select>`, too many options) — but as of the taxonomy lockdown (see below), typing a name that isn't in the list is **rejected**, not auto-created. If the galactic war adds/removes planets and this list needs updating, re-run the scrape and replace `DEFAULT_PLANETS` — don't re-add per-user editability to work around it.
- **The whole taxonomy is fixed, not user-editable, including denominations now**: POI types, item types (name/icon — value is separately computed, see above), difficulties, factions, planets, *and* Drop Size Tracker denominations. This was a deliberate simplification once the user considered the built-in defaults complete for what they want to track. First pass left read-only reference lists for the first five in Settings, but that still looked/felt editable (same list styling as everything else in an otherwise-editable panel) — the user asked for those to just be removed, so **Settings has no display of POI/item/difficulty/faction/planet lists at all** (no `renderConfigLists()`/`renderNameOnlyConfigList()`/`#poi-config-list` etc. — all gone, not hidden). If you want to see the taxonomy, it's visible in context: item icons/names on the Tally page and the Drop Size Tracker section of Stats, difficulty/faction in the mission-entry dropdowns, planets via the searchable Planet field. Denominations were the last holdout (still add/removable) but got locked too — see the next bullet.
- **Drop Sizes only covers Medals, Requisition, and Super Credits** — `dropSizeStatsHtml()` filters `config.itemTypes` to `(i.denominations || []).length > 0`, which is how Weapons/Common Samples/Rare Samples get excluded (their `denominations` array is `[]`): those always give exactly 1 per pickup per the user, so there's nothing to break down. The three shown items' denomination sets are fixed (Medals: 1/2/3, Super Credits: 10/100, Requisition: 100/1000, set in `DEFAULT_DENOMINATIONS` in `config.js`) — no add/remove UI anywhere. `state.removeDenomCount`/`api.deleteDenomRemote` were removed as dead code earlier (the server's `DELETE /api/denominations` endpoint was left in place, just unused by the client).
- **POI display names are `Bunker` / `Container` / `Loot Pod`** (ids unchanged: `two_man_bunker`/`explodable_bunker`/`loot_pod`) — renamed from "Two-Man Bunker"/"Explodable Bunker" for brevity on the Tally page. Because names are app-owned text with no rename UI, `loadConfig()` now has a second reconciliation pass (right after the existing merge-missing-defaults pass) that overwrites `entry.name` for every already-present id from `DEFAULT_CONFIG`, across all five taxonomy lists — this is what makes a rename in `config.js` actually reach users with a pre-existing cached `sg_config` in `localStorage`, instead of silently sticking with whatever name was cached from install time. If you rename anything else in the fixed taxonomy going forward, this pass already covers it automatically — no extra migration code needed.
- **Medals/Requisition/Super Credits are tallied directly on the Tally page now, not only on Drop Sizes** — each of their `item-row`s on a POI card renders a `.btn-denom-pick` button per fixed denomination (e.g. Medals: `+1 +2 +3`) instead of a generic `+`. Clicking one does three things at once: bumps that POI's per-mission `itemDrops` count (as before), calls `state.incrementDenomCount(itemId, denom, 1)` (the same lifetime tally Drop Sizes reads/writes), and POSTs it to the server immediately if one's set — so a diver never has to re-enter the same pickup on a second page. Requested explicitly ("don't have to double count things on different pages"). The single `−` button that remains rolls back *both* the mission item count and that specific denom bucket, using an in-memory-only `denomPickStacks` map (keyed `poiId:itemId` → LIFO array of denoms picked, push on `item-inc-denom`, pop on `item-dec`). This is a stack, not a single last-value — picking `+3` then `+2` and pressing `−` twice correctly rolls back the `2` first, then the `3`, in reverse order, however many picks deep. (First version only remembered the single most recent pick, so a second `−` press silently stopped rolling back denom tallies while still decrementing the visible count — caught when the user asked "what would happen if I hit minus after adding a 3 then a 2," walked through it, and fixed it before it shipped as a real bug.) The stack resets on page reload (in-memory only), so an undo after a reload just decrements the item count with no denom-tally rollback — acceptable, not the common misclick path. Items with no `denominations` (Weapons, Common/Rare Samples) are untouched — still a plain `−`/count/`+` triplet. Don't reintroduce a plain `+` for the three denominated items without being asked, and don't regress the stack back to a single last-pick.
- **The minus button's own label shows what it will undo** — plain `−` when the stack for that row is empty, `−2`/`−1000`/etc. (the top of `denomPickStacks`) once there's a pick to roll back, via the `.minus-labeled` class (`width:auto` override on `.btn-count`, since Requisition's `1000` doesn't fit the fixed tap-target square). Requested explicitly ("show the last added item somewhere") after walking through the multi-pick-then-multi-undo scenario together. Note: a static-HTML-snapshot-plus-headless-screenshot trick doesn't work for visually verifying *post-interaction* state here — `main.js` re-executes fully on real page load and reads real (empty) `localStorage`, discarding whatever a jsdom script baked into the serialized DOM. Verify interaction-dependent UI via jsdom functional assertions (see `smoke28.mjs` in conversation history) instead; screenshots are only useful for a page's *initial* render.
- **`.denom-pick-group` is one joined segmented pill (single shared border, internal 1px dividers, `background: transparent` per segment), not 3 separately-boxed `.btn-denom-pick` buttons.** First pass gave each denom button the same filled-box treatment as every other button on the card (`+1 FOUND`, `−`, plain `+`) — with 3 of them per denominated item × 3 denominated items per card, it read as a dense wall of identical boxes with no hierarchy ("looks kinda bad" feedback). Fixed by (a) making the picker a single outlined pill so 3 buttons register as one control, not three, (b) keeping the bold olive fill (`#1f2a12` bg + yellow-dim border) reserved for genuinely primary actions (`+1 FOUND`, `New Mission`) and (c) adding a subtle `border-bottom` between `.item-row`s so rows separate by whitespace/rule instead of by button-box edges. If adding more per-row controls later, default to the subdued/outline treatment and reserve the filled-olive style for the one primary action per card.
- **`.item-row` is a CSS grid (`icon | name | controls`)** — superseded on the Tally page by the tile+popup split below, but the *shape* (grid-area icon/name/controls, controls always ending in the "add" mechanism) is worth knowing if you touch `.item-row-desktop` or the log-edit-form's plain `.item-row`. When touching either, verify a ~900px and a ~400px viewport via headless `chromium --headless=new --screenshot=...` (no chromium-cli in this sandbox, but a plain system `chromium` binary is present and works fine for this).
- **The Tally page renders two completely different item UIs depending on `window.innerWidth`, chosen in JS (not a CSS media query) — mobile gets tap-to-open tiles + `#item-popup`, desktop gets the classic always-expanded inline rows back.** The tile+popup design (previous two entries) turned out to be worse on desktop: opening a popup for every single pickup is an extra tap for no benefit when there's already room to show every control inline. So `js/main.js` tracks `isMobileLayout` (`window.innerWidth <= MOBILE_BREAKPOINT_PX`, currently `640`) as module state, re-checked on `resize` (not just at load — narrowing a desktop window live should still switch modes, and does: see `smoke33.mjs`'s resize-crossing test). `renderPoiGrid()` branches per item on this flag: mobile emits `.item-tile` (opens the popup on click), desktop emits `.item-row-desktop` (grid layout, `.item-controls` inline, same visual shape the old always-inline design had). Both modes share the exact same mutation logic — `tallyItemInc`/`tallyItemDec`/`tallyItemIncDenom` in `main.js` — called either from `#item-popup`'s click handler (mobile) or directly from `#poi-grid`'s click handler when it sees `.item-row-desktop` in the click path (desktop); don't fork the tallying/undo-stack logic itself again, only the *presentation* differs.
  - **jsdom has no `window.matchMedia` at all** (confirmed empirically: `typeof window.matchMedia === 'undefined'` in this project's jsdom version) — this is why the breakpoint check uses `window.innerWidth` directly rather than `matchMedia`, and why every test touching Tally-page item rendering must explicitly set `dom.window.innerWidth = <value>` *before* importing `main.js` (jsdom defaults to `1024`, which is desktop mode) — forgetting this makes `.item-tile`/`#item-popup` selectors resolve to nothing in a "mobile" test, or `.item-row-desktop` resolve to nothing in a "desktop" test. `smoke32.mjs` (mobile, `innerWidth = 375`) and `smoke33.mjs` (desktop, `innerWidth = 1200`, plus the resize-crossing case) are the reference tests for each mode.
  - Investigated a "buttons don't show up on mobile" report by screenshotting the popup at 320px/375px viewports (real headless Chromium renders, not just jsdom) — every control rendered correctly at every width tested, no reproduction. Most likely explanation given this project's history (see the cache-busting entry above — this exact "UI silently broken" symptom has happened twice before, both times a stale cache): a hard refresh should be the first thing to try if this comes up again, before assuming a new CSS bug.

- **Drop Sizes has no interactive UI anywhere anymore — it's a read-only "Drop Sizes" section inside the Stats page's tab content, right alongside POI Frequency/Resource Yield/etc.** This went through two intermediate shapes before landing here, both superseded — worth knowing if you find references to either in old context: (1) originally its own nav page (`DROP SIZES`) with `.denom-card`s you tallied with `+`/`−` buttons; (2) briefly a second always-visible panel on the Stats page, still with those same interactive `+`/`−` buttons and a local/global stacked count per row. Once the Tally page could tally denominations inline (see the `.btn-denom-pick` entries above), the user pointed out tallying would *only* ever happen from Tally going forward ("one interface with missions and such counting there"), so a second place to edit the same numbers was pointless — Stats should "just show the stats... like probs and counts," matching how every other section on that page already works. So: `renderDenomPage()`, `#denom-grid`, `.denom-card`/`.denom-row`/`.denom-avg`/`.denom-count-stack` and friends, and the `on('denom-grid', 'click', ...)` handler are all gone (CSS included). In their place, `dropSizeStatsHtml(tally)` in `main.js` renders a `barChartHtml()` + `<table class="stats-table">` per item (Size / Count / % of Pickups) — the exact same visual language as the rest of `statsHtml()` — and `renderStats()` appends its output to **both** `#stats-mine` (fed `state.getDenomTally()`) and `#stats-global` (fed `globalDenomTally`), so it now correctly respects the My Stats/Global Stats tab split like everything else on the page (earlier versions showed local+global simultaneously in one card, which no longer applies). It's still *not* filtered by the squad/difficulty/faction/planet row — pickup size isn't tied to any of those — so `dropSizeStatsHtml` takes a raw tally, not a `stats` object from `computeStats`. Don't reintroduce any per-bucket `+`/`−` controls outside the Tally page without being asked — the whole point of this change was consolidating tallying to one place.

- **`globalMissions` (the array Global Stats renders from) now refreshes on every sync pass, not just on a `GLOBAL STATS` tab click.** Bug report: "global stats updating when people delete missions doesn't work super well." Root cause — `refreshGlobalStats()` (the function that re-fetches `globalMissions` and calls `renderStats()`) was only ever invoked from the tab button's own click handler. So a mission deleted by another diver, or even your own delete if the Global tab happened to already be selected before you navigated away to the Missions page, would sit stale in your cached `globalMissions` indefinitely — nothing re-fetched it until someone happened to re-click that exact tab. The denom (Drop Sizes) side never had this problem, because `refreshGlobalDenoms()` was already called from `syncPendingMissions()`'s periodic 30s interval; missions just never got the same treatment. Fix: `syncPendingMissions()` now also calls `await refreshGlobalStats();` (self-heals within 30s for everyone, matching the denom pattern), and the `log-delete` handler now calls `refreshGlobalStats()` directly (when a server is set) instead of a plain `renderStats()`, so your own deletes reflect immediately rather than waiting for the next interval tick. `log-save` (edit) already called `syncPendingMissions()` at the end, so it picked up the fix for free. Tested by simulating "another diver deletes elsewhere" via a raw out-of-band `fetch(...DELETE...)` bypassing this client's own UI entirely, then confirming the stale cached count self-heals without any tab click — see `smoke31.mjs` in conversation history.

- **Tally page items are tap-to-open tiles + a popup, not always-expanded inline rows.** Requested explicitly ("make it work well on mobile... click the type, input the resources"). A POI card previously showed all 6 item types as fully-expanded rows (icon, name, `−`/count/`+` or the denom-pick pill) all at once — on a phone that's a lot of vertical scroll and small stacked controls per card. Now `renderPoiGrid()`'s `.poi-items` is a compact grid of `.item-tile`s (icon + name + a small count badge that only appears once count > 0), and tapping one opens `#item-popup` (a centered, `position:fixed` card, reused `.settings-overlay` for the dimmed backdrop) showing exactly what the old inline row showed — same `−`/count/denom-pick-group or `−`/count/`+`, same undo-stack, same minus-label-shows-what-it-undoes behavior — just relocated. All the actual tallying logic (the `item-inc`/`item-dec`/`item-inc-denom` handling, `denomPickStacks` push/pop) moved from `poi-grid`'s click handler to a new delegated handler on `#item-popup` itself; `poi-grid`'s handler now only handles `poi-inc`/`poi-dec` (the POI-level "+1 FOUND" counter, unchanged) and `item-tile-open` (calls `showItemPopup(poiId, itemId)`).
  - The popup **stays open across multiple taps** (`openItemPopup = { poiId, itemId } | null` module-level state, `renderItemPopupIfOpen()` re-renders its content in place after every tally) — closing after each tap would defeat the point for someone tallying several pickups of the same item back to back. It only closes on an explicit close (✕ button or tapping the overlay backdrop), or programmatically via `closeItemPopup()` when a mission ends/resets (`new-mission-btn`, `reset-data`, JSON import) — those clear `currentMission`/`itemDrops` wholesale, so a popup left open across that boundary would otherwise show stale counts until next tap.
  - The tile grid itself stays in sync live while the popup is open, since every popup tally still calls `renderPoiGrid()` alongside `renderItemPopupIfOpen()` — the tile's count badge updates in the background even though you're looking at the popup.
  - `.item-row`/`.item-name` still exist in CSS/HTML but now *only* style the Mission Log's edit form (simple icon+name+number-input rows, unrelated to the Tally page) — don't assume `.item-row` means "Tally page item" anymore when grepping.
  - Old tests that clicked denom-pick/`item-inc`/`item-dec` buttons directly inside `.item-row` (`smoke20/23/26/27/28/30.mjs` in conversation history) needed updating to first tap `.item-tile` then act inside `#item-popup`; `smoke26/27/28` were retired outright since `smoke32.mjs` re-covers the same undo-stack/minus-label scenarios end-to-end through the new popup flow.

- **Tapping "+1 FOUND" now launches a guided pick-item → pick-amount loop that repeats until the POI's slots are actually filled, instead of leaving "mark it found" and "log what dropped" as two disconnected actions.** Requested explicitly, describing the desired order verbatim: "click on type of container to add -> click on option to add -> click on amount -> repeat option amount until container full." `#item-popup` now has two modes (`openItemPopup.mode`): `'single'` (the existing tap-a-tile-directly behavior, unchanged) and `'guided'` (new). Guided mode's `itemId` starts `null` (pick-item step — one tile per item type, reusing the `.poi-items`/`.item-tile` grid *inside* the popup) and gets set once you tap one; if that item has denominations it shows the amount step next (reusing `.denom-pick-group`), otherwise it auto-tallies `+1` immediately since there's nothing to pick. After every tally, `guidedAdvanceOrClose()` checks `slotsFilled(poiId) >= totalSlots` (the exact same numbers already driving the `SLOTS TALLIED: X / Y` progress bar) — if full, closes the popup; if not, resets to the pick-item step and loops. `totalSlots` is `poiCounts[poiId] * p.slots`, so finding a *second* container of the same type mid-session correctly resumes at "slot 4 of 6" rather than restarting at 1 — the loop is driven by the aggregate progress number, not a per-find counter. Closing early (✕ or overlay tap) just stops prompting without forcing completion; the item tiles/desktop rows remain available afterward to fill in whatever's left manually, same as before. This isn't gated to mobile — desktop's "+1 FOUND" opens the same guided popup, since the point is sequencing the two logging steps together, not compactness (that's what the mobile-vs-desktop tile/row split, previous entry, already handles). `tallyItemInc`/`tallyItemDec`/`tallyItemIncDenom` are unchanged and shared by all three entry points (single-mode popup, guided-mode popup, desktop inline rows) — don't fork the actual tallying logic per mode, only `itemPopupHtml()`'s presentation branches.

- **Bug: the guided flow's slot target scales with how many times "+1 FOUND" was tapped, not the POI card's fixed "N SLOTS" label — tapping it more than once (double-tap, ghost-touch, or just tapping it again without realizing what it does) inflates the target with no visible explanation, making the loop feel stuck/infinite.** Reported as "loot pod, somehow got stuck adding infinite medals, had to X out" — reproduced exactly by dispatching two `poi-inc` clicks on a 1-slot Loot Pod: `totalSlots` becomes `2 * 1 = 2` instead of `1`, so the flow correctly (but confusingly) asks for a 2nd full item+amount round the user never intended. Root cause is inherent to the design (`totalSlots = poiCounts[poiId] * p.slots`, see the guided-flow entry above) — not something to "fix" by capping it, since finding multiple containers legitimately should ask for more slots. The actual gap was that the popup gave no indication *why* it kept asking, and no way to correct an over-tap without abandoning the flow (close, hunt for the tiny `−` button on the card behind the popup, reopen). Fixed by surfacing it directly in the popup: when `foundCount > 1`, both guided-mode steps (`itemPopupHtml()`) show `"N found so far — tapped +1 FOUND more times than intended? Undo one."` with a `.btn-link` (`data-action="slot-fix-found"`) that calls `guidedDecrementFound()` — decrements `poiCounts[poiId]`, then runs the same `guidedAdvanceOrClose()` check used after every normal pick, so it can immediately close the popup outright if the corrected target is already met. Doesn't touch already-tallied item drops (those need the normal per-item undo if they're wrong too) — it only fixes the *found* count driving how many more rounds get asked for.

- **The guided pickup flow (previous entry) is togglable in Settings → "Guided Pickup Flow"** — `state.getGuidedFlowEnabled()`/`setGuidedFlowEnabled()`, key `sg_guided_flow_enabled`, defaults to `true` (unset → on, same saved-vs-default pattern as `getServerUrl()`). Requested explicitly: "make that UI togglable when using desktop mode too — some might want it." One setting, not per-mode — it governs whether `poi-inc` calls `startGuidedFlow()` at all, checked as `if (state.getGuidedFlowEnabled()) startGuidedFlow(poiId);`, so turning it off just makes "+1 FOUND" mark the container found with no popup, same on mobile and desktop; tallying then falls back to the tiles (mobile) / inline rows (desktop) exactly like before this whole feature existed. Doesn't affect "single" mode (tapping an item tile/row directly) at all — that always worked, and still does, regardless of this toggle. Not included in JSON export/import — it's a UI/behavior preference local to a device, same category as `serverUrl`/last-selected dropdowns, not mission data. `.toggle-row`/`.toggle-switch` in `css/style.css` is a hand-rolled checkbox-driven switch (real `<input type="checkbox">`, visually hidden, `.toggle-switch` styled via the `:checked` sibling selector) — first checkbox-based control in the app, reuse this pattern rather than inventing another one if more on/off settings get added.

- **`crypto.randomUUID()` only exists in "secure contexts"** — HTTPS, or the `localhost` origin specifically. Reported as "on other devices: crypto.randomUUID is not a function" — the repro is testing from a second device by hitting the dev machine's LAN IP over plain HTTP (`http://192.168.x.x:8080`, the `python3 -m http.server` workflow from this file's "Running the frontend" section): that's *not* a secure context even though the host machine's own `localhost` access is, so `crypto.randomUUID` is simply undefined there (the parent `crypto` object still exists — only the method is gated). Both call sites (`state.js`: `getClientId()`'s Diver ID generation, `blankMission()`'s mission id) now go through a local `generateId()` helper that falls back to a `Math.random()`-based v4-shaped UUID string when `crypto.randomUUID` isn't a function. Fine to not be cryptographically unpredictable here — same trust model as the rest of the app (no private data). If you add another spot that needs a random id, use `generateId()`, not `crypto.randomUUID()` directly. **Testing note**: jsdom's `crypto.randomUUID` lives on `Crypto.prototype`, so `delete window.crypto.randomUUID` on an instance does *not* remove it (prototype methods aren't own-properties); to actually simulate its absence in a test, assign over it instead — `dom.window.crypto.randomUUID = undefined;` — confirmed via `Object.getOwnPropertyDescriptor` that it's `writable`/`configurable` so a plain assignment shadows the prototype correctly (see `smoke38.mjs`).

- **`.item-tile` (mobile grid + guided-popup item-picker) is a fixed 2-column grid, not `auto-fill`, with bigger icons/text than the first pass.** Feedback: "text might feel a little small, but also there isn't enough space for all the images and such." Root cause of the "not enough space" half: `grid-template-columns: repeat(auto-fill, minmax(84px, 1fr))` packs in as many 84px+ columns as fit, so near the mobile/desktop breakpoint (POI cards go single-column and can be up to ~640px wide) it could cram in 5-6 tiny tiles instead of a controlled, generously-sized set — switched to `repeat(2, 1fr)` so tile size stays predictable and large across the whole mobile range instead of shrinking as the card gets wider. Icon size for tiles specifically went from the shared 32px (`.item-icon`/`img.item-icon`, still 32px everywhere else — item rows, popup headers, log-edit-form) to 44px via a `.item-tile .item-icon`/`.item-tile img.item-icon` override, and `.item-tile-name` from 12px to 14px. Verified readable at 320px (iPhone SE width, the narrowest common target) via screenshot, not just the usual 375px.

- **Global text-size pass**: feedback was "in general the text was too small" (not scoped to the tiles fixed in the previous entry). Every `font-size` in `css/style.css` between 11px and 16px got bumped one or two steps up a consistent scale, applied via `sed` in a specific non-cascading order (process from the *highest* source value down — `16→17` before `15→16` before `14→16` before `13→15` before `12→14` before `11→13` — otherwise an earlier rule's output becomes a later rule's input and things get double-bumped): `11→13, 12→14, 13→15, 14→16, 15→16, 16→17`. Note `14px` and `15px` both land on `16px` — an intentional minor tier collapse, those two were already close enough visually that keeping them distinct wasn't worth preserving. The base `html, body { font-size: 17px }` was untouched (never a source in the 11-16 range). If adding new small text, match this scale rather than reaching for `12px`/`13px` again.
- **Quick-add bar** (`#quick-add-bar`, top of the Tally page, `position: sticky; top: 0`) — one button per POI type (`+ BUNKER`, `+ CONTAINER`, `+ LOOT POD`), rendered from `config.poiTypes` by `renderQuickAddBar()` (called once at init, plus after JSON import in case `config` changed). Requested explicitly: "I don't want to deal with scrolling to add a loot pod vs a bunker." Clicking one does exactly what that POI's own "+1 FOUND" button does — both now go through a shared `foundPoi(poiId)` (increments `poiCounts`, persists, re-renders, and calls `startGuidedFlow()` if the Guided Pickup Flow setting is on) — don't let these two call sites drift apart. Sticks to the very top of the viewport once scrolled past its normal position (`main` has 22px padding; the bar cancels it with `margin: -22px -22px 0` so it spans edge-to-edge when stuck, rather than floating indented). `z-index: 50` — below the settings overlay (100), item popup (150), and toast (200), so those still correctly cover it. Verified the click→`foundPoi` wiring thoroughly via jsdom; the actual `position: sticky` *rendering* can't be meaningfully asserted through jsdom (`getComputedStyle` returns browser defaults since jsdom doesn't load external stylesheets) or cleanly through a headless-Chromium full-page screenshot either (full-page capture mode renders sticky elements oddly, showing what looks like a duplicate — a known headless quirk, not a real bug) — trust the CSS technique itself here (a plain, extremely well-supported `position: sticky; top: 0`) rather than chasing a pixel-perfect screenshot of the stuck state.

- **"Revamp the mobile UI to feel smoother" — added real open/close transitions (fade/scale/slide) to the item popup, its overlay, the settings panel, and the toast, plus tactile `:active` press feedback on buttons/tiles, instead of the previous instant `display:none` toggles and flat color-only presses.** `display:none` can't itself be transitioned (the browser can't interpolate across it), so a naive `opacity` transition on `.hidden`'s target state never actually animates — `showAnimated(elm)`/`hideAnimated(elm)` in `main.js` solve this: `showAnimated` removes `.hidden` then waits **two** `requestAnimationFrame`s (one isn't reliably enough — a single frame can get coalesced with the same paint in some browsers, silently skipping the "just appeared, still at rest" frame the transition needs to start from) before adding `.is-open`, which is what each element's CSS actually transitions toward; `hideAnimated` reverses it, removing `.is-open` immediately (starts the fade-out) and re-adding `.hidden` only after the transition finishes — bounded by a `transitionend` listener *and* a 250ms fallback `setTimeout` (belt-and-suspenders: `transitionend` might not fire cleanly for an already-at-rest element or under `prefers-reduced-motion`). `openPopup()`/`closeItemPopup()` (item popup + its overlay) and `openSettings()`/`closeSettings()` (settings panel + its shared `.settings-overlay`) all route through these two helpers now — don't revert them to plain `classList.add/remove('hidden')`, that's exactly the instant-snap behavior being fixed. `toast()` intentionally does **not** reuse `hideAnimated` — a toast firing again while a previous one is mid-fade-out is a realistic scenario (two `toast()` calls close together), and `hideAnimated`'s generic `transitionend` listener would incorrectly fire off the *new* toast's entrance transition and yank it away early; `toast()` instead tracks two of its own plain timers (`toast._timer`, `toast._hideTimer`) that both get cleared at the top of every call.
  - `@media (prefers-reduced-motion: reduce)` sets `transition-duration`/`animation-duration` to `0.001ms` globally — deliberately *not* `transition: none`, because `transition: none` would stop `transitionend` from ever firing, and `hideAnimated` would then always fall through to the slower 250ms timeout fallback even for users who explicitly asked for *less* motion, which is backwards.
  - **Testing gotcha**: `main.js` calls bare `requestAnimationFrame(...)`, which — same as `document`/`localStorage`/`confirm`/`Blob`/`URL` already listed in every smoke test's setup block — resolves against the outer Node `globalThis` under `runScripts: 'outside-only'`, not against `dom.window`'s own scope. Every test file needs `globalThis.requestAnimationFrame = dom.window.requestAnimationFrame.bind(dom.window);` alongside the other globals, or any code path that opens a popup throws `ReferenceError: requestAnimationFrame is not defined`. Also: jsdom **never fires `transitionend`** (confirmed empirically — it doesn't run a real layout/animation engine), so every test that checks "popup/settings closed" state now needs `await new Promise((r) => setTimeout(r, 300))` after the closing action, to clear `hideAnimated`'s 250ms fallback — checking immediately/synchronously after a close action will incorrectly read as "still open" now. Checking *open* state needs no such wait (`showAnimated` removes `.hidden` synchronously).

- **"Simplified View" — the mobile tile+popup layout and the guided pickup flow (both previous entries) are now ONE user-facing toggle, right on the Tally page, not two separate mechanisms (a Settings-only guided-flow switch, plus width-based auto-detection nobody could see or override).** Requested explicitly: "the guided stuff and phone view should be the simplified view, togglable on the main screen itself." `#simplified-view-toggle` lives in `.poi-panel-header` (next to the "POINTS OF INTEREST" title, same `.toggle-row`/`.toggle-switch` markup as the old Settings toggle, just relocated) and drives a single module-level `simplifiedView` boolean in `main.js` that both `renderPoiGrid()` (tiles vs `.item-row-desktop`) and `foundPoi()` (`if (simplifiedView) startGuidedFlow(poiId);`) read. Backing state is `state.getSimplifiedView()`/`setSimplifiedView()`, key `sg_simplified_view` — deliberately returns `null` (not a default `true`/`false`) when nothing's saved, so `main.js` can distinguish "no preference yet, guess from `window.innerWidth <= 640`" from "user explicitly chose one." **The old resize listener that silently re-detected mobile-vs-desktop on every window resize is gone entirely** — once this became a visible, user-controlled switch, letting a resize event override it out from under the user would defeat the entire point of giving them direct control. The width check only ever runs once, at first load, as a starting guess, and is never persisted until the user actually flips the toggle themselves. The old Settings → "Guided Pickup Flow" section, `state.getGuidedFlowEnabled()`/`setGuidedFlowEnabled()`, and the `sg_guided_flow_enabled` key are gone too, not deprecated-and-kept — replaced outright, no migration, since the feature was only one session old. If you find old context referencing `isMobileLayout` or "guided flow" as a separate concept from layout, it's stale — they're unified now.
- **Added a "🗑 CLEAR (DON'T SAVE)" button next to "NEW MISSION — SAVE & RESET"** for discarding an in-progress mission that's garbage (misclicks, wrong POIs entirely) without it landing in history or getting synced anywhere. `state.discardCurrentMission(config)` is deliberately *not* built on top of `completeMission()` — it skips the `history.push()`/`saveHistory()`/sync entirely and just calls the same internal `blankMission()` + `saveCurrentMission()` that `completeMission()` uses for its "fresh" half, so a clear can never accidentally leak into the mission history the way a refactor-by-reuse of `completeMission()` might invite later. Confirmed via `smoke40.mjs`: after tallying and clearing, both local history (`state.getHistory()`) and the server's `/api/missions` are empty, and a subsequent normal "New Mission" still saves correctly afterward (clearing doesn't leave the mission lifecycle in a broken state). Gated behind the same `confirm()` pattern as the other destructive actions in this app (Reset All Local Data, mission delete) — never skip that confirmation for a new destructive button without being asked.

- **The quick-add bar only renders/shows in Simplified View** — `renderQuickAddBar()` now toggles `.hidden` on `#quick-add-bar` based on `simplifiedView` first thing, and returns early (skipping the button markup entirely) when it's off. Requested explicitly: "Simplified view should have the + things at the top, non simplified view shouldn't... I want this to fit on the screen without scrolling." Reasoning: the bar solves scrolling-to-a-card specifically in the tile+popup layout, where a card can be compact enough to scroll out of view easily; in the inline-row layout every card's full controls (including its own "+1 FOUND") are already always on screen, so the sticky bar was just redundant vertical space there. `index.html`'s `#quick-add-bar` starts with `class="quick-add-bar hidden"` in the raw markup now (was unclassed before) purely to avoid a flash-of-empty-bar before `init()` runs, matching how other JS-driven sections (`#stats-page` etc.) already start hidden by default. Call `renderQuickAddBar()` again (not just `renderPoiGrid()`) anywhere `simplifiedView` changes, or the bar's visibility goes stale. Note for future work: removing this bar helps but doesn't fully solve "fits without scrolling" at typical laptop viewport heights — 3 POI cards × 6 full inline item rows is inherently a lot of vertical content in the non-simplified layout; further compacting (if ever requested) would need to touch row height/spacing, not just this bar.

- **Above 960px viewport width, `#tally-page` becomes a 2-column grid** — mission-meta panel as a ~240-300px sidebar (`grid-column: 1`, its own contents switched to a vertical stack via `flex-direction: column` overrides on `.mission-meta-grid`/`.mission-actions`/`.squad-select`/`.btn`), POI panel taking the remaining width (`grid-column: 2`), with `#tally-page`'s own `max-width` bumped from the base `main` rule's 1150px to 1700px. Requested explicitly: move the mission config off the top so "the main UI" (the POI cards, what's actually in use live) gets more room, plus give POI more horizontal room since item names (`.item-row-desktop`'s `1fr` name column) were wrapping onto two lines when 3 cards had to share a comparatively narrow 1150px total. Both problems traced back to the same root cause — not enough total width — so both got fixed by the same change: widening the container *and* getting the sidebar out of the POI panel's way nets meaningfully more room than either change alone (900+px per card at typical wide-desktop widths, up from ~350px), which incidentally also means all 6 item rows now fit in a card without scrolling on many screens, something the "fit without scrolling" ask from two turns ago never fully achieved just by removing the quick-add bar. Gated purely by `@media (min-width: 960px)` — independent of the `simplifiedView` JS toggle (see two entries up), since a wide window benefits from the extra room regardless of which Tally-page interaction mode is active. Below 960px, falls back to the original single-column stack (mission panel above POI panel, full width) — there isn't room for a usable ~300px sidebar plus a readable POI area below that. If `.mission-panel`'s base flex layout or `.poi-grid`'s `auto-fit` column logic changes later, re-check this media query still makes sense against the new numbers.

## Server data model (as of the denominations addition)

Two tables, both self-contained (no server-side canonical config/taxonomy — see "No server-side canonical config" above):
- `missions` — one row per mission, keyed by client-generated UUID `id`. Upsert on POST; ownership-checked (see above).
- `denominations` — one row per (client_id, item_id, denom), i.e. "this diver's count of pickups that gave this exact amount of this item." Composite primary key **is** the ownership boundary (a client can only ever address its own rows), so no separate check needed there. `GET /api/denominations` (no `clientId`) returns everything for global pooling; `main.js`'s `refreshGlobalDenoms()` sums counts per (item, denom) client-side and feeds that into `stats.resolveItemValues()`.
